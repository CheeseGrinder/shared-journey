# 11 — Limitations and open issues

Three kinds of entries, kept separate:

- **A. Suspected defects** found while reading the code. Not reproduced in game; each says
  how to confirm it.
- **B. Accepted limitations** documented by the authors (code comments, `../../README.md`,
  `TODO.md`).
- **C. Documentation gaps** between the repository documents and the code.

## A. Suspected defects

| ID | Area | Finding | Why it matters | How to confirm |
|----|------|---------|----------------|----------------|
| L-01 | Block colours | **Fixed (uncommitted).** `assets/sharedjourney/palette/vanilla.json` was missing from the repository (no file, no history; an empty `palette/` folder existed), although `BlockPalette` and `../../CLAUDE.md` rely on it; a dedicated server has no vanilla client textures, so vanilla blocks would have degraded to `MapColor`. Regenerated with `tools/PaletteGenerator.java` against the Minecraft 1.21.1 client jar: 1059 of 1062 blockstates extracted; `processResources` packages it. | Colours of the whole map | Start a dedicated server and look for "Loaded bundled block palette: N blocks" (and no "not found" warning); regenerate on every Minecraft version bump |
| L-02 | Sync | The periodic delta fires when `gameTime % syncRateTicks == (entityId & 15)`. With `syncRateTicks < 16` (allowed range starts at 5) a player whose `entityId & 15 ≥ syncRateTicks` never matches: they only get the join delta, the handshake delta and immediate render pushes. | Stale far regions for those players | Set `syncRateTicks=5` and check `/sj stats` of players with different entity ids |
| L-03 | Banner waypoints | `BannerWaypointPayload` encodes the name with `writeUtf(name, 48)`, but `BannerWaypointService.onPlace` does not truncate; the anvil allows 50-character item names. Encoding a 49–50 character name throws, and the entry is persisted *before* the send, so the same failure can repeat at each login (`sendAllTo`). Public and private waypoints are truncated; banners are not. | Possible network error/disconnect for a name that is legal in vanilla | Rename a banner to 50 characters, place it |
| L-04 | Sync | `onPlayerJoin` queues a delta immediately, i.e. before the handshake can arrive (the client hashes its cache asynchronously first). The queue is not pruned when the handshake later seeds `sentVersions`, so already-owned regions of that first window are sent anyway. The comment in `onPlayerJoin` claims pushing starts after the handshake. | Wasted bandwidth at each login (bounded by the push window) | Watch `regionsSent` in `/sj stats` right after a reconnect with a full cache |
| L-05 | Waypoints | Public waypoints have **no ownership or permission check**: any player can overwrite or delete any public waypoint. | Griefing on open servers | Delete another player's public waypoint with a second account |
| L-06 | Persistence | Waypoint JSON files (`waypoints_public.json`, `waypoints_banners.json`, `waypoints_auto.json`, `waypoints/<uuid>.json`, client `waypoints.json`) are written with a plain `Files.writeString` (truncate then write), unlike regions and indexes (INV-6). A crash mid-write can leave a truncated file; the loaders log the error and start empty. | Waypoint loss after a crash | Kill the process during a write |
| L-07 | Memory | Region images, public variants, cached PNGs and hover regions loaded by the server are **never evicted**. A region image costs ≈ 1 MiB of ints plus its cached PNG, per layer and per cave band; a large world with 5 layers and 12 bands can keep a large number of MiB resident. | Server memory growth on big explored worlds | `/sj stats` shows RAM regions and an estimate |
| L-08 | Sync / I/O | `SyncService.drainQueue` runs on the server main thread and calls `MapManager.dataOf`, which lazily loads and decodes the region file (`ImageIO.read`) and encodes the PNG on first access: disk and CPU work on the tick thread, against the engine's own rule that the main thread only resolves chunks (G-2). | Occasional tick hitch when a player first needs a cold region | Profile the first sync of a large, never-loaded region |
| L-09 | Radar | The radar cap (`radarMaxRadius`) is announced to clients and honoured by the client's drawing code; the radar only draws entities the client already tracks. A modified client can ignore the cap, though it cannot see entities the server never sent. | The cap is advisory, not an enforcement | — |
| L-10 | Layer transition | The previous-layer stand-in ([07 LT-01](07-client-ui.md)) cannot tell "still loading" from "nothing exists on the new layer": for 1.5 s after a switch, a region that has no texture on the new layer (e.g. unexplored cave band) shows the previous layer's image before turning to plain background. Chained switches (A→B→C inside the window) stand in with B only, which may itself be missing. | Brief wrong-layer imagery after a switch | Switch DAY→CAVE over a region never explored underground |
| L-11 | Client cache | Disk loads are asynchronous ([03 ASM-05](03-sync-protocol.md)), so right after login or a fresh map open the first frames can show unloaded regions as background (uploads are budgeted per frame, 8 loads in flight) where the old synchronous load drew them at once; since the level-of-detail work ([03 ASM-06](03-sync-protocol.md)) the same holds for a region the server pushes while no texture of it is resident: it appears a few frames after it arrives instead of in the same frame. `isChunkPainted` (fullscreen CAVE hover) answers false until some level of the band image is in RAM. | Cosmetic, first frames only | Open the fullscreen map zoomed far out on a large cached world |
| L-12 | Radar rules | The `kind` of an entity type is judged from the first entity of that type the radar sees and cached ([12 RRL-15](12-radar-rules.md)); a mod that reuses one entity type for several classes would be classified by whichever instance came first. A rule file is validated only against its own syntax: a `type` or `tag` that does not exist (typo, absent mod) is silently a rule that never matches, not a logged error. | A rule that seems ignored | Write `{ "type": "minecraft:zomby" }`, reload: no warning, no effect |
| L-13 | Client sync | The fullscreen map requests the INFO hover sidecar (≈ 65 KB per region on real caches) of **every** visible region, whatever the zoom ([07 FM-07](07-client-ui.md)), and re-requests keys it does not own every 5 s (≤ 64 per frame), including regions that do not exist. Zoomed out on a large world this is hundreds of sidecars over the bandwidth cap plus up to a few thousand keys per 5 s, although at that zoom hover precision is moot. The level-of-detail work deliberately leaves it alone: the chunk overlays treat a present INFO sidecar as "this region is explored" ([13](13-chunk-overlays.md)). | Network and disk volume when zoomed far out on a big world | First open of the fullscreen map at minimum zoom on an uncached world: watch `/sj stats` bytes sent and the cache folder grow |
| L-14 | Client cache | The `.lod` sidecars ([01 CLI-05](01-regions-layers-storage.md)) are never garbage-collected: one whose PNG was rewritten stays on disk, stale, until that region is next drawn reduced; one whose PNG was removed outside `/sj purge` stays forever. They add ≈ 35 % of a region PNG's size to the cache. | Disk usage only | Compare cache folder size before and after a far-zoom visit |
| L-15 | Client cache | With the disk cache on, a region pushed while no texture is resident is shown only through the disk (or the in-flight write buffer, [01 CLI-06](01-regions-layers-storage.md)); if the file write fails (disk full, read-only folder) the region never appears, where it used to be displayed from RAM for the session. | Missing tiles on a failing disk | Make the cache folder read-only and walk into unexplored territory |

## B. Accepted limitations (documented upstream)

| ID | Limitation | Source |
|----|------------|--------|
| B-01 | World edits by pistons, fluids and explosions are partially covered; chunks changed while unloaded refresh at their next dirty mark or load. | README |
| B-02 | Custom layers: no per-dimension config/ops toggle (active everywhere; the renderer may return null), no vertical bands, generic icon; the ops layer editor and `/sj admin layer` handle built-ins only. | README, `LayerRegisterEvent` |
| B-03 | JourneyMap bridge covers waypoints and the overlay types used by common integrations; themes, mapping events (beyond start/stop) and other API surfaces are acknowledged and ignored. | README |
| B-04 | Quarantine: trust at region granularity (two quarantined spots in a region cross-reveal to players near either), crash loses `.pub` sidecars (early reveal), banners of hidden players broadcast normally, witnesses recorded before the witness feature are lost. | `QuarantineService` |
| B-05 | Named banners placed by world generation, commands or non-entity placement are not detected. | `BannerWaypointEvents` |
| B-06 | Create train route simulation stops at branches without a recorded decision and may slightly overshoot at crossings. | `CreateTrainPathService` |
| B-07 | Mob icons: render layers (sheep wool, armor, profession) not drawn; bounds cached per entity type; fixed reference pose. | `MobHeadIcons` |
| B-08 | Minification flicker of thin Create rail lines at low zoom (rail buffer sampled without mipmaps). Fixing it needs mipmaps on Create's texture or a custom texel-AA shader (TODO P5). Underground rail overlay was implemented and reverted (poor result, high cost). | `../../TODO.md` |
| B-09 | The local player marker is a vector triangle until a texture asset is supplied (TODO P3). | `../../TODO.md` |
| B-10 | The API toolbar buttons have no overflow handling, a fixed ~64 px reservation per bridged widget, ItemStack icons only, and toggle outlines refresh only on press/rebuild. | `FullMapToolbarEvent` |
| B-11 | The fullscreen map is always north-up; rotating it would be a dedicated project. | `../../TODO.md` |
| B-12 | Cache integrity detects accidental or casual tampering of a client's own cache files; it is not authentication against a malicious client (which could compute any hash). It protects the client's display consistency, not the server. | design |
| B-13 | Player positions (dimension, x, z) of every non-hidden player are broadcast to everyone without distance limit — by design, that is the shared-map feature. Hiding is opt-in. | design |
| B-14 | Server engine settings (`engine.*`) and the worker count are file-only and read at start; there is no in-game editor for them. | `OpsConfigService` |
| B-15 | Minimap frame textures ([07 §2.1.1](07-client-ui.md)): straight square edges are stretched along their side (themes are uniform along the edge, no repeating pattern or per-edge ornaments); the round strip has finite angular resolution (512 texels), fine for smooth materials but it blurs sharp angular detail on very large minimaps; themes are bundled only (a resource pack can replace the PNGs but not the per-theme band geometry, which is fixed in code); the visual match of `CLASSIC` with the former procedural border was checked on a simulation of the sampling, not in game. | `MinimapFrame`, `tools/MinimapFrameGenerator.java` |
| B-16 | Radar height fade ([07 RDR-06..08](07-client-ui.md)): entities never fade out completely (opacity floor 0.25); the fade distances are not coupled to the fixed ±32 block query window, so a full-fade distance above ~32 is never reached by a drawn entity; the arrow and label placement (right of the icon, fixed offset) was not checked against every icon size in game; fullscreen labels do not avoid overlapping neighbouring icons. | `RadarHeightFade` |
| B-17 | Radar rules ([12](12-radar-rules.md)): `tamed` / `owner` cover `TamableAnimal` only (wolves, cats, parrots; tamed horses and llamas are not "tamed" for rules, so they stay passive as before); only living non-player entities can be drawn (no dropped items or projectiles); no per-rule icon override or dot size (only `iconScale` of head icons and the dot color); the rule files have no in-game editor and no generated template (copy the bundled `default.json`); player skin heads are not rule-driven. | design |
| B-18 | Chunk overlays ([13](13-chunk-overlays.md)): (a) the slime pattern of a large explored area leaks information about the world seed (each chunk answers a 1-in-10 test of a seeded generator); the seed is never sent and data is limited to explored regions, but a determined client could search the seed space — the only full remedy is `overlays.slimeChunksEnabled=false`; (b) the explored gate has region granularity (one mapped chunk exposes the 1 024 chunks of its region), and force-loaded chunk positions can reveal chunk loaders in explored regions; (c) the forced set is polled once per second per dimension (O(forced chunks) per check, only for dimensions players asked about), so a change shows up with up to ~1 s latency; (d) the two server flags are file / NeoForge-config-screen only, not in the ops tab; (e) the slime overlay is not drawn below 0.25 px per block and neither overlay is drawn when a view covers more than 2 500 regions; (f) the flagged chunks are drawn on every layer, including cave bands where slime spawning (below y = 40) is relevant only to some of them; (g) the minimap has no toggle button, only the settings screen. | `ChunkOverlayService`, `ChunkOverlayRenderer` |
| B-20 | Level of detail ([07 §3.5](07-client-ui.md)): (a) only the fullscreen map uses reduced levels, the minimap always draws level 0; (b) they need the disk cache (the PNG on disk is the source) and are off with `map.diskCache = false`; in that mode textures of regions that are not on disk are never released by the memory cap (they could not be reloaded), so a far-out view of a big world costs full images as before; (c) the first far-zoom visit of a region decodes its PNG (≈ 4 ms with a Java decoder, measured on real cache files; the game's decoder was not timed) and writes a sidecar, later visits read the sidecar; level 1 is never stored and is always rebuilt from the PNG; (d) the memory cap is an estimate (twice the RGBA size per texture), not a measurement of the GPU driver's allocation; (e) the level is a pure function of zoom and GUI scale, with no hysteresis, no mipmaps and no anisotropy: at a non-integer ratio a reduced level is sampled at 1 to 2 texels per pixel with bilinear filtering, which is smooth but slightly soft; (f) the feature was verified by unit-level checks of the pixel code and a successful build, not yet in game. | `LodChain`, `ClientMapCache` |
| B-19 | Automatic waypoints ([06 §3.4](06-waypoints.md)): (a) only created on a player action — a bed or anchor that was never used to set a spawn, a portal nobody went through (or that only mobs and items crossed), and anything that existed before the feature was added are not detected; (b) cleanup is by break event for beds/anchors broken by a player and otherwise a 200-tick check of tracked positions in loaded chunks, so a block removed while its chunk is unloaded keeps its waypoint until the chunk loads; (c) a respawn anchor drained by a respawn is still an anchor block, so its waypoint stays although the spawn is gone (the next spawn change or breaking the block removes it), and a bed whose spawn vanilla invalidated (obstructed, missing at respawn) is handled the same way; (d) portal markers are capped at 256 world-wide (further portals ignored with a warning) and, being shared, can be created by any non-hidden player; (e) the canonical portal position assumes rectangular vanilla portals (a modded portal block shape with the same block is treated alike); (f) names and group labels are resolved in the receiving client's language when the payload arrives (a language switch applies after the next resync); (g) the client's local hidden-id set keeps ids of removed automatic waypoints (harmless; the id is the same if the block is re-created). The behavior relies on NeoForge firing `PlayerSetSpawnEvent` / `EntityTravelToDimensionEvent` / `PlayerChangedDimensionEvent` for bed, anchor and portal use. | `AutoWaypointService`, `AutoWaypointEvents` |
| B-21 | Converted waypoints ([14](14-converted-waypoints.md)): (a) the link is per waypoint and one-directional: linking an Overworld waypoint shows it in the Nether, it does not create a Nether waypoint, and the two ends are never matched against each other; (b) the counterpart position is plain arithmetic (x8 / ÷8, Y kept and clamped to 0..127 towards the Nether), not snapped to any real portal, so the portal vanilla actually links to may differ; (c) only the vanilla Overworld and Nether are paired, and banner, automatic, bridged and TEMP waypoints cannot be linked; (d) a public waypoint's link can be toggled by any player ([L-05](#a-suspected-defects) applies); (e) with `waypointStorage = CLIENT` the server switch is enforced by the client only, which is acceptable since the counterpart is purely visual; (f) the counterpart is not listed in the manager nor counted in group totals, "View on map" and teleport apply to the source only; (g) the "(converted)" name suffix is resolved when the dimension index is rebuilt, so a language change shows it after the next waypoint mutation. | `WaypointStore`, `DimensionConversion` |

## Acceptance checks

For each A-entry, the "How to confirm" column is the acceptance test of the fix. B-entries
are not defects: they are checked only to make sure a change does not silently remove the
documented mitigation (e.g. the 250 ms path throttle, the 128-key request cap).
